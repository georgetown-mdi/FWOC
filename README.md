# FWOC

The Federal Workforce OpenCommons (FWOC) is a public data platform for United States federal civilian employment data, at <https://opencommons.mdi.georgetown.edu>. This repository holds the R/Arrow pipeline that builds the FWOC microdata: it assembles records released by the Office of Personnel Management (OPM) from 1973 to the present into three harmonized, labelled Parquet datasets, validates them, and exports them for publication. It also holds the codebook and example code for working with the published data.

The repository contains code, documentation, and small metadata only. The source data, the built datasets, and the public export are fetched or generated by the pipeline and are never committed.

## Using the published data

You do not need this pipeline to use the data. The Download page at <https://opencommons.mdi.georgetown.edu> serves each dataset as zipped Parquet, CSV, and Stata files, with employment split by agency.

- `quick_start_code/01_download_subset.R` downloads a subset (one dataset, chosen agencies, a range of months) as Parquet files, and `02_open_subset.R` shows how to open the result without loading it into memory and how to save a piece as CSV or Stata. Both need only the `arrow`, `dplyr`, and `jsonlite` packages.
- `docs/fwoc_codebook.qmd` is the codebook: one entry per published variable, with definitions, types, coverage, and value labels. It is rendered to PDF with Quarto and published on the site. The table it is built from is `metadata/codebook/fwoc_codebook_table.csv`.

## The data

The pipeline combines two sources of OPM administrative records:

| Source | Short name | Period used | Status |
|---|---|---|---|
| OPM records released under three FOIA requests and [placed in the public domain by BuzzFeed News](https://archive.org/details/opm-federal-employment-data) | BZ | 1973-09 through 2004 | Frozen |
| [Federal Workforce Data](https://data.opm.gov/), OPM's data site | FWD | 2005 to present | New month released monthly; earlier months are sometimes revised |

The BuzzFeed releases run to 2017-03, but only their pre-2005 rows reach the final datasets. The 2005–2017 overlap between the two sources is used to validate one against the other.

The pipeline produces three datasets ("hives"), each partitioned as `year=yyyy/month=m/` with the month not zero-padded:

| Hive | Contents | Coverage |
|---|---|---|
| `emp_hive` | Employment: end-of-period snapshots of the workforce | Quarterly from 1973-09 through 2011-06, monthly thereafter |
| `acc_hive` | Accessions: employees joining an agency | 1982 to present |
| `sep_hive` | Separations: employees leaving an agency | 1982 to present |

Where FWOC publishes its own version of an OPM variable, the FWOC version carries a `_fwoc` suffix and sits beside the OPM original: `agency` is OPM's label and `agency_fwoc` is FWOC's. `metadata/codebook/fwoc_codebook_table.csv` documents every published variable, including the few OPM columns the pipeline corrects in place, and `metadata/codebook/opm_fwoc_differences.csv` lists each place the FWOC agency and subagency labels differ from OPM's.

`metadata/labels/*_labels_fwoc_experimental.csv` are an unfinished attempt to classify every change in OPM's agency and subagency names. They are joined during the build and dropped before publication; they stay in the repository for transparency, and `metadata/publish/variable_manifest.csv` records why.

## Repository layout

```
00_build_fwoc.R     Runs the whole build in order
01_ ... 17_         Numbered pipeline steps (there is no 06; see setup/build_labels.R)
setup/              Builds the pipeline's inputs: label tables, BLS series, renv.lock
utils/              Helper functions sourced by the scripts
crosswalks/         Builds the occupational category (PATCO) crosswalk
aggregate/          Builds the aggregate tables behind the FWOC dashboards
validation/         Post-build validation suite
codebook/           Rebuilds the codebook table from the built hives
docs/               The codebook, as a Quarto document (_quarto.yml renders it from the root)
quick_start_code/   Example scripts for downloading and opening the published data
metadata/           Small committed inputs: OPM code tables, label tables, crosswalks,
                    validation baselines, the codebook table, the variable manifest
```

The repository root is the project root. Run every script from there; all paths in the code are relative to it.

Generated at the root, and ignored by git: `buzz_feed/`, `data_opm_gov/`, `emp_hive/`, `acc_hive/`, `sep_hive/`, `aggregate_data/`, `export/`, `validation_output/`, `logs/`.

## Requirements

- **R 4.6.1** and the packages in `renv.lock`, which records the exact versions the pipeline was last run with. Install them with `renv::restore()`.
- **Linux.** The export step (16) stages its files in `/dev/shm` and calls `zip`, `xargs`, and `rsync`. Steps 01–15 use only R.
- **Quarto**, only to render the codebook. Render it from the repository root with `quarto render docs/fwoc_codebook.qmd`; it reads `metadata/codebook/gap_detail.csv`, which `codebook/02_codebook_build.R` writes and git ignores, so on a fresh clone the build must run first.
- **Disk.** A full build takes about 400 GB: roughly 60 GB of BuzzFeed data and staging, 55 GB of OPM downloads, 60 GB of final hives, and 220 GB for the public export.
- **Memory.** The scripts stream through Arrow and never load a whole hive. The pipeline is developed on a machine with 24 cores and 250 GB of RAM and has not been tested on smaller ones.
- **Time.** A monthly build takes roughly three to seven hours on that machine, depending on whether the codebook and export steps run.

## Acquiring the raw inputs

**BuzzFeed FOIA data.** Download the three releases from the [Internet Archive](https://archive.org/details/opm-federal-employment-data) and arrange them under `buzz_feed/data/`, one folder per release, each split into `dod/` and `non-dod/`:

```
buzz_feed/data/
  1973-09-to-2014-06/    SCTFILE.TXT, dod/, non-dod/   (each with status/ and dynamic/)
  2014-09-to-2016-09/    dod/, non-dod/                (each with status/, accessions/, separations/)
  2016-12-to-2017-03/    dod/, non-dod/                (each with status/)
```

`SCTFILE.TXT` is OPM's code table file from the first release. `setup/build_duty_station_labels.R` parses it into `metadata/labels/duty_station/ds_labels.RData`, which is committed, so that script needs running only if you want to regenerate the file.

**Federal Workforce Data.** Step 03 downloads the employment, accessions, and separations files from the [data.opm.gov API](https://data.opm.gov/get-data/api-access) into `data_opm_gov/`. No API key is needed. The step downloads only what is missing, keeps every version OPM has published, and records the files it used in `metadata/fwd/file_manifest.csv`.

**OPM code tables.** The code tables and data dictionary that the labels are built from are committed under `metadata/code_tables/`, each with its download date in the file name. For a monthly refresh, download the current tables from data.opm.gov into that folder and move the previous set into `metadata/code_tables/prior_downloads/<YYYY_MM>/`, so the setup chain can compare the two.

**BLS series.** `setup/get_bls_data.R` downloads CPI-U and the national and state unemployment rates from the Bureau of Labor Statistics. BLS requires a descriptive User-Agent that identifies you, so set one before running setup, for example in `~/.Renviron`:

```
BLS_USER_AGENT="Your Name your@email.org"
```

## Running the pipeline

### 1. Setup

```
Rscript setup/00_run_setup.R
```

Setup takes under a minute and is meant to be watched. It writes `renv.lock`, compares the OPM code tables against the previous download, rebuilds the label tables in `metadata/labels/`, and downloads the BLS series.

If OPM's code tables changed since the previous download, setup writes a change report to `metadata/code_tables/change_reports/` and stops. Review the report, then acknowledge it and re-run:

```
FWOC_METADATA_ACK=1 Rscript setup/00_run_setup.R
```

Review the resulting changes under `metadata/` and commit them before building.

### 2. Build

```
Rscript 00_build_fwoc.R
```

The build runs each step in a fresh R process, appends all output to `logs/fwoc_build_log_<timestamp>.txt`, and halts at the first step that fails. To resume after a failure, comment out the completed steps in `00_build_fwoc.R` and run it again.

**First run on a fresh clone:** steps 01 and 02, which parse the BuzzFeed releases, are commented out in `00_build_fwoc.R` because that data never changes. Uncomment them for the first build, then comment them out again for the monthly cycle.

The build has four phases:

| Phase | Steps | What it does |
|---|---|---|
| Assemble | 01–04 | Parse the BuzzFeed releases and download and assemble the FWD files into staging hives |
| Harmonize and enrich | 05–15 | Bring the two sources to one schema, write the final hives, attach labels, derive the FWOC variables, join the BLS series, and set the published column order |
| Aggregate and validate | `aggregate/`, `validation/` | Build the dashboard tables, then run the validation suite |
| Document and publish | `codebook/`, 16, 17 | Rebuild the codebook table, export the public files, and upload them |

Validation is a gate: if any hard check fails, the codebook, export, and upload steps do not run.

### 3. Validation

`validation/00_run_validation.R` runs six exercises and writes its reports to `validation_output/`:

| Exercise | Checks |
|---|---|
| 1. Overlap | BZ against FWD over the period both cover, and FWD revisions against the recorded baseline |
| 2. Labels | Every valid, in-range code has a label |
| 3. Reconciliation | Row counts in the final hives equal the source counts for every period |
| 4. Conformance | Published columns and types match the codebook, and no period is missing |
| 5. Sanity and history | Indicator and domain checks, and row counts of past periods against the recorded history |
| 6. Aggregates | The dashboard rate tables reconcile to the hives |

The files in `metadata/validation/baselines/` record the known, accepted discrepancies. When exercise 5 reports that the row count of a past period changed, it prints the change as an allowlist row. If you accept the change, add that row, with a reason, to `ex5_history_allowlist.csv` and re-run.

### 4. Export and publication

Step 16 writes the public export to `export/`, in the layout the Download page serves: `parquet/hive/` (the partitioned hives), `parquet/zip/` (each hive zipped), and `csv/` and `stata/` (accessions and separations as single files, employment as one or more files per agency under `agency/<code>/`).

Step 17 and `aggregate/push_to_gcs.R` upload to the FWOC project's own cloud storage. They are included for transparency and you will not have write access to those buckets. To publish your own build, point them at storage you control. Step 17 refuses to upload unless `FWOC_PUBLISH=1` is set, so a routine build never publishes by accident; `Rscript 17_push_to_r2.R --dry-run` previews an upload without changing anything.

### Environment variables

| Variable | Used by | Purpose |
|---|---|---|
| `BLS_USER_AGENT` | `setup/get_bls_data.R` | Identifies you to the BLS download server; required |
| `FWOC_METADATA_ACK` | `setup/check_opm_metadata.R` | Set to `1` to acknowledge a reviewed change in the OPM code tables |
| `FWOC_PUBLISH` | `00_build_fwoc.R`, `17_push_to_r2.R` | Set to `1` to allow the upload of the public export (requires `rclone`) |
| `FWOC_GCS_DEST` | `aggregate/push_to_gcs.R` | Destination bucket for the dashboard tables (requires `gcloud`) |

## Working with the hives

Open a hive lazily with Arrow and reduce it before collecting; the employment hive is far too large to load whole. `quick_start_code/02_open_subset.R` walks through this in more detail.

```r
library(arrow)
library(dplyr)

open_dataset("emp_hive", unify_schemas = TRUE) |>
  filter(year == 2024, month == 12) |>
  count(agency_fwoc) |>
  collect()
```

`CLAUDE.md` records the conventions the pipeline code follows, including the Arrow idioms that keep it within memory. It is written for AI coding assistants and is also a useful summary for contributors.
